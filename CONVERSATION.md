### 2. The Reverse Engineering Question

**Efe:** "şimdi o zaman ben o dmg yi reverse engineering yapsam, kendi gemini auth um ile geminiyi sanki tarayıcıdan kullanıyormuş gibi kendi uygulamamdan kullanabilir miyim?"

Perplexity explained the full picture:
- The app almost certainly uses the official Gemini REST API or an internal Google endpoint
- Reverse engineering approaches: static analysis (strings, Hopper/Ghidra), network sniffing (Charles Proxy/mitmproxy), runtime hooking (Frida)
- Key insight: **if it uses the official API, you already have access via AI Studio — no reverse engineering needed**
- If it uses internal endpoints (like `gemini.google.com` web UI), those require OAuth session tokens
- ToS warning: unofficial usage risks account bans

---

### 3. The Free Tier Problem

**Efe:** "ama ai studiodan key aldığımda hemen bitiyor. fakat geminiyi kullanabiliyorum uzun süre."

This is the core insight that led to everything. Perplexity explained:
- The Gemini web UI (`gemini.google.com`) uses a **completely separate, much more lenient** rate limiting system than the API
- The cookie-based approach: `__Secure-1PSID` + `__Secure-1PSIDTS` cookies from your browser session
- The existing open-source library: [`HanaokaYuzu/Gemini-API`](https://github.com/HanaokaYuzu/Gemini-API) — a reverse-engineered Python wrapper
- It hits `https://gemini.google.com/_/BardChatUi/data/assistant.lamda.BardFrontendService/StreamGenerate` directly
- Supports Gemini 2.5 Pro/Flash, Imagen4, multi-turn chat, PDF/image input, thinking output

---

### 4. Playwright vs Cookie Wrapper

**Efe:** "mesela normalde bunu playwright ile soruları cevapları fln alabiliriz değil mi? ama bu sefer daha hafif olacak değil mi?"

| | Playwright | gemini-webapi |
|---|---|---|
| Chromium instance | Full browser | None |
| RAM | ~300-500MB | ~20-50MB |
| First response | 3-5s (boot) | <1s |
| Stability | Breaks on DOM changes | API-level, more stable |

The cookie wrapper makes **direct HTTP POST** requests — no browser, no DOM parsing.

### 6. The Big Idea

**Efe:** "peki öyle bir agentic orkestrasyon ve prompt organizasyonu yapsak ki... sonra bizim yarattığımız machine, kendi kendine çalışacak ve tek amacı hayatta kalmak olacak. hayatta kalma kriteri de şu aslında, text olarak hayatta kalmaya çalışacak. soru sorup cevap alması onun hayatta kalabildiği anlamına gelecek."

This was the moment. A **self-preserving agent** with a single fitness criterion: can it receive a text response from any LLM?

The survival loop:
```
[Agent] → try wrapper → response? → alive ✅ → sleep → repeat
                               ↓ no response
                    ask another model to write a new wrapper
                    → install it → test it → continue
```

Perplexity designed the full architecture: survival loop, wrapper pool, codegen layer, SQLite memory.

## Key Insight

The entire project is built on one observation: **web UI rate limits are far more generous than API rate limits**, because services treat browser users differently from programmatic clients. By authenticating as a web user (via session cookies), the agent gets much longer survival time per service.

With 11 services in the pool — 7 with free official APIs, 4 with cookie-based access, and local Ollama as a fallback — the agent has extremely high survival probability.
